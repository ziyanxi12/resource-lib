## P7 · 怎么做到的（工作流）

### 宏观·项目级流程

1. **需求输入 → AI 生成设计方案**
   - 阶段产物：`DESIGN.md`（489 行，含技术选型、数据库表结构、API 设计、目录规范）
   - AI 承担设计职责，非仅代码生成

2. **人工审查方案 → 确认实施**
   - 审查设计方案是否满足业务需求
   - 人工决策节点：确认后进入开发阶段

3. **按设计文档开发**（进入任务级循环，见下）

4. **首版交付后生成项目导引 → 持续演进**
   - 产物：`CLAUDE.md`（编码规范、时间处理、序列化、命名归一化）
   - 目的：约束 AI 后续修改代码时遵循既有规范
   - 非项目起点，而是首版验证后的规范化沉淀
   - 随项目迭代 7 次（加表 → 统一命名 → 大重构 → 看板 → 图表样式）

### 微观·任务级循环（vibecoding 核心机制）

| 步骤 | 执行方 | 说明 |
|------|--------|------|
| ① 输入需求与验证要求 | 人 | 明确功能需求及测试验证标准 |
| ② 输出修改方案 | AI | 不直接编码，先提供实施方案 |
| ③ 确认方案 | 人 | 人工卡点，审查方案可行性 |
| ④ 实现并自测 | AI | 按确认方案编码，执行测试验证 |
| ⑤ 确认交付 | 人 | 验证无误后闭环，进入下一次循环 |

**叙事要点**：
vibecoding 采用双循环工作流——项目级（设计→审查→开发→规范沉淀）与任务级（需求→方案→确认→实现→验证）。核心特征是每个环节均设人工决策卡点，AI 生成方案而非直接编码，确保产出可控。

## P10 · 质量兜底（怎么避免 AI 翻车）

- **规范层**：`CLAUDE.md` 编码规范（时间处理、序列化、命名等统一约定）
- **审查层**：人工审查所有 AI 生成代码
- **测试层**：单元测试 + e2e（Playwright）
- 结论：AI 不会自动发现设计性错误，靠规范 + 审查兜底

## P11 · 边界与风险（诚实汇报）

**vibecoding 适合**：
- 从 0 到 1 的全栈系统、文档驱动型项目
- 增量功能开发、原型快速验证

**vibecoding 不适合**：
- **少量函数的精确修改**——AI 上下文切换成本高于手写，得不偿失
- **高保密项目**——外部模型存在数据外泄风险
- **强依赖内网环境的项目**——内网模型能力通常弱于外网，"在外网能改好的代码，在内网可能改不好"

**当前局限**：
- 仍依赖人工审查兜底，AI 不会自动发现设计性错误
- 复杂调试链路（跨服务、时序问题）AI 容易绕圈

## P12 · 结论

**效率结论**：
- 核心系统从 0 到首次上线：约 2 周（46 commits / ~3,100 行）
  ——覆盖五类资源管理、CRUD、向量搜索，可用的生产级核心
- 后续持续迭代至当前版本：约 6 周（85 commits）
  ——新增分组/来源管理、搜索日志、应用管理、白名单/超管、
    宽高回填、语义理解、性能基准等
- 关键不是"2 个月做完整套系统"，而是"2 周核心上线、之后持续增强"
  ——vibecoding 的真正效率杠杆：从想法到可用，极短

**推广建议**：
- 短期：优先在"从 0 到 1 的新建项目、低保密场景"试点
- 中期：随模型能力升级，边界会持续外扩
- 不建议：在保密 / 内网 / 精确小改场景强推
